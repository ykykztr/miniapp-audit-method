# 微信小程序「信任边界」审计方法

> 一份从实战里提炼出来的方法笔记。目标不是教你打某个具体的系统，而是给你一套**可迁移**的流程：拿到一个小程序，判断它声称校验的东西里，**哪些是真的、哪些只是摆设**。
>
> 全文用占位符代替具体目标，你可以把 `SAMPLE_UNIVERSITY` / `APP_URL` / `<TOKEN>` 换成自己的对象。

---

## 这套方法解决什么问题

很多系统的安全结论是「看起来有校验」—— 代码里在读 GPS、在读信号强度、在读设备标识。但**「代码读了它」和「服务端验了它」是两件完全不同的事**。

典型的安全剧场长这样：

```
客户端：读取 GPS → 放进请求体 → 发给服务端
服务端：收下 GPS → 存进数据库 → 从不拿它做任何判断
```

从代码上你只能看到"它读了 GPS"，永远看不出"服务端拿它做了什么"。**唯一的办法是把请求构造出来，一次改一个变量，看服务端对什么说了不。**

这套流程就是干这个的。

## 一句话版方法

1. **解包**拿到客户端代码（或直接抓包）
2. **搜索**定位认证相关的 API 调用，读出「客户端声称它提交了什么」
3. **构造请求**，逐条验证服务端到底对什么做了判断 —— **一次只改一个变量**
4. 把结论整理成「**服务端验了什么 / 没验什么**」，而不是「我找到了一串能用的参数」

第 3 步是全部价值所在。前两步只是准备。

---

## 一条要提前建立的认知

**认证强度 = 伪造一个通过校验的请求所需的成本。**

不是「有多少道校验」，不是「用了多少种技术」，而是：

> 攻击者要付出多少，才能让服务端说「通过」？

如果答案是「知道一个公开下发的编号」，那这套认证的强度就是**「知道一个公开下发的编号」**—— 哪怕它有蓝牙、有 GPS、有信号强度、有五道状态机。

**判断这个问题，只能靠构造实验。**

---

## 免责与边界

这套方法是**审计思路**，用于：

- 理解自己所用系统的实现（学习、写技术笔记）
- 在自己有授权的系统上做验证
- 判断某个设计的实际安全强度

**不要**把某次审计得到的具体参数、完整链路公开传播 —— 那会把风险转嫁给该系统所有其他使用者，而且你自己也留了名。**方法可以分享，参数不行。**

体育打卡系统也适用
